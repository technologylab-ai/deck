1What deck is

deck is a small macOS CLI driven one target at a time by Elgato Stream Deck buttons (deck open <target>). It opens an app or a browser tab on a specific AeroSpace workspace idempotently: if the thing is already open, focus it and switch to its workspace; otherwise open it, place it, and switch. Presses must feel instant.

Targets are config-only (~/.config/deck/targets.toml); a target’s type/browser selects one of three backends behind a single interface — app (native, via open -b), safari (AppleScript), and chrome. This document is about chrome, which was by far the hardest to get right.

The original assumption Synadia Google apps live in Safari; personal apps (HEY) live in Chrome. Because they’re in physically different browsers, dedup never needs to be profile-aware — the browser boundary is the isolation. That held. What broke was the unstated assumption that there is one Chrome.

2The incident

Phase 1 worked in testing. Then a real press of deck open hey did the worst possible thing: instead of focusing the existing, logged-in HEY, it opened a brand-new, logged-out HEY in a throwaway Chrome profile — complete with Chrome’s first-run “Choose your search engine” screen. The user, reasonably, was furious: “even if there was no tab, it should not create a new profile!”

Two things were broken at once, and untangling them drove the whole design:

  • Detection failed — it didn’t find the open HEY tab.
  • Creation went to the wrong place — the fallback spawned a window in a junk profile, not the real one.

3Root cause: there were three Chromes

The user runs extra Chrome instances on purpose — for OBS window-capture, slide switching, and a browser-based demo (launched via earlier guidance, and a permanent part of the setup). At the moment of the bug, ps showed three main Google Chrome processes:

4056   Google Chrome                                  # default profile — the real browser, logged-in HEY
31102  Google Chrome --app=…/presentation.html  --user-data-dir=~/.obs-chrome-slides
34814  Google Chrome --app=http://localhost:14801 --user-data-dir=~/.obs-chrome-ui

All three share bundle id com.google.Chrome. And here is the load-bearing fact of this entire document:

The trap When several processes share one bundle id, an Apple Event sent with tell application "Google Chrome" is delivered to one instance chosen by macOS — and you cannot choose which from the high-level application "name" specifier. On this machine it deterministically landed on an --app instance that has no scriptable browser windows.

The evidence was unambiguous:

$ osascript -e 'tell application "Google Chrome" to count windows'
0          # …returned 0 five times in a row, while the real browser had 12 windows

$ osascript -e 'tell application "Google Chrome" to get URL of active tab of front window'
execution error: Can’t get window 1. Invalid index. (-1719)

So find() saw zero tabs → reported “not open” → create() ran AppleScript make new window inside that same wrong instance, whose --user-data-dir is a throwaway profile → logged-out window with the first-run screen. Every symptom explained by one cause. (“New Chrome available,” the user’s first guess, was a red herring.)

4Two problems that need different tools

Separating these was the key to not chasing one solution for both:

ProblemWhat it needsHard part
Detect — is a tab for this URL open? Read tab URLs in the default-profile Chrome. Reaching the right instance; seeing background tabs, not just the active one.
Focus — bring that exact tab + its workspace forward. Select a specific tab, then switch AeroSpace. Selecting a tab needs to act on Chrome, not just read it.

A method can solve one and not the other. The on-disk session file, for instance, can detect any open URL but can never focus a tab. That realization is why the final design uses one mechanism that does both.

5Every approach we weighed — and the verdict

ApproachSees real profile?Background tabs?Can focus?Verdict & why
Plain AppleScript
tell app "Google Chrome"		 no no no Rejected. Routes to a random same-bundle instance. Permanently unreliable as long as any --app Chrome runs — which is always.
CDP
--remote-debugging-port		 no yes yes Rejected. Chrome 136+ ignores the flag on the default profile for security. Would force a separate profile + a fresh HEY login — losing the real session.
Isolate the OBS Chromes to another bundle (Chromium/Beta) yes yes yes Rejected. Brittle: it breaks again the next time any --app Chrome is launched. Pushes the problem onto the user’s workflow.
Disk session file (SNSS) yes yes no Detection only. Proved the open HEY URL was discoverable on disk — but it can’t switch tabs, so it can’t complete a press.

6The journey, step by step

The order matters, because each step taught the constraint that ruled out the next-simplest idea.

  1. Fix the rage bug first: never spawn a junk profile.

    Replaced AppleScript make new window in create() with Google Chrome --new-window <url> (no --user-data-dir).

    Why it works: launching the binary with no profile flag hands the URL to the running default-profile instance — it printed Opening in existing browser session — so it lands in the real, logged-in profile and can never create a throwaway one. Detection was still broken, but the worst symptom was gone.

  2. Prove detection is even possible.

    Found the open HEY URL in Chrome’s on-disk session file (…/Profile 1/Sessions/Session_*).

    Lesson: macOS can tell a tab is open — the AppleScript path was the problem, not the OS. But disk can’t focus a tab, so it’s not a complete answer.

  3. Confirm the routing is truly unfixable from AppleScript.

    Activating the default instance first (open -b, open -a) did not change which instance the Apple Event reached — still 0 windows, still -1719.

    Lesson: high-level tell application "name" gives no control over instance selection. Dead end confirmed, not assumed.

  4. Build the AX approach (user’s choice at the time).

    Discovered each Chrome window exposes its active tab’s URL as the window-level AXDocument attribute — instant, no traversal, PID-attributed. Wired find() to read it and bridge the window title to the AeroSpace window-id; focus() via aerospace focus --window-id. It worked.

    Observed: AXDocument = https://app.hey.com/ on the “Imbox” window; aerospace focus --window-id 456 jumped from Slack (ws 7) to HEY (ws 1).

  5. The challenge that broke AX.

    The user switched the HEY window to another tab and said: “find it.” Now no window had AXDocument = app.hey.com; HEY was a background tab. Probing the tab strip via AX found nothing and a full entire contents traversal took 114 seconds.

    Hard limit learned: AX never exposes a background tab’s URL (the tab strip isn’t in the tree without forcing full accessibility mode, which System Events can’t set). AX was a ceiling, not a floor.

  6. The breakthrough: address Apple Events to a PID.

    SBApplication.alloc().initWithProcessIdentifier_(4056) talks to that exact process, bypassing bundle-id routing. It returned the full scripting dictionary of the real browser.

    Observed: 77 tabs enumerated across all windows; HEY found as window#0 tab#0 https://app.hey.com/ while that window’s active tab was Gemini — the precise case AX could not see.

  7. Ship it as a real dependency.

    Added pyobjc-framework-ScriptingBridge to deck so it runs as plain deck (reproducible, no ad-hoc environments). Reverted the permission model from Accessibility back to Automation; doctor checks it.

    Verified live: deck open hey jumped to HEY from a background tab, with no duplicate window and no stray profile.

7How it works now

One mechanism — ScriptingBridge addressed to the default-profile Chrome PID — does detection and tab selection; AeroSpace does the workspace move.

  1. Pick the PID. Among the real Google Chrome processes (no helpers/renderers), choose the one launched without --user-data-dir — the default-profile browser. The --app instances are deliberately ignored.
  2. Attach. SBApplication.initWithProcessIdentifier_(pid) — Apple Events now go to that process only, immune to how many Chromes are running.
  3. find(). Scan every window’s every tab for target.match (substring of the URL). Background tabs included. Read-only.
  4. focus(). Set the window’s activeTabIndex to the match, raise the window, activate Chrome.
  5. Follow with AeroSpace. Bridge the window title to its AeroSpace window-id and run aerospace focus --window-id, which focuses the window and switches to its workspace.
  6. create() (only if not found). Google Chrome --new-window <url> in the default profile, then place + switch the new window via AeroSpace.
The title bridge ScriptingBridge reports a window’s title as the bare page title (Imbox); AeroSpace (and AX) report Imbox - Google Chrome - Rene. So the match is a prefix match. The AeroSpace window-id is captured from the window’s pre-switch title and stays valid after the tab changes, so the focus is race-free.

9Permissions model

Both browser backends drive the browser via Apple Events, so both need Automation permission — granted to the app that runs deck, not to deck itself:

  • Development: your terminal (here, Ghostty) → Google Chrome & Safari.
  • Production: the Elgato Stream Deck app, since button presses run under it.

The first Chrome press shows a one-time macOS “deck wants to control Google Chrome” prompt. In practice no prompt appeared on first run, because the terminal already held Automation→Chrome from earlier work — TCC keys the grant to the controlling app, which deck inherits. deck doctor reports the status for every browser the config uses.

Superseded The short-lived AX design needed Accessibility permission (granted to Ghostty during that phase). The final design does not use AX — that grant can be removed.

10Known limits & future

  • Dedup needs a running default-profile Chrome. If only --app instances are up, find() returns nothing and create() opens a fresh default-profile window — which is the desired outcome anyway.
  • Only the default profile is queried — on purpose. deck targets one PID (your real browser); the --app --user-data-dir Chromes are ignored. A tab living only in a separate --user-data-dir profile wouldn’t be found. If that ever matters, add a per-target profile/user-data-dir field in targets.toml so a target can name which instance to query.
  • Phase 3 (Stream Deck wiring) is done — see §11. Phase 2 (mode = "app" → --app=<url> windows) is still ahead. The ScriptingBridge dedup already generalizes to app-mode windows, since they’re just windows/tabs in the same default-profile instance.
The one-line takeaway If you remember nothing else: the user runs several Chrome instances under one bundle id, so address Chrome by PID with ScriptingBridge — never by name with AppleScript. Everything else follows from that.

11Phase 3: Stream Deck wiring & icons

The buttons run a dedicated Elgato SDK v2 plugin (ai.technologylab.deck), not a third-party command-runner. The plugin is deliberately thin: it holds no logic and shells out to ~/.local/bin/deck for everything — dropdown ← deck list --json, button image ← deck icon, tap → deck open, long-press → deck close. All the real behavior stays in Python and testable from a terminal, and adding a target to targets.toml needs no plugin change.

  • Absolute shim path, always. Stream Deck launches commands with a minimal PATH (no Homebrew), so the plugin invokes ${HOME}/.local/bin/deck by absolute path — the same reason deck calls aerospace/osascript/Chrome by absolute path internally.
  • Tap vs. long-press. Stream Deck fires keyDown/ keyUp but doesn’t classify a hold. The action arms a 500 ms timer on keyDown; if it fires while still held it runs deck close and marks the press handled, so keyUp doesn’t also open. A normal release before 500 ms cancels the timer and runs deck open. Close acts on the threshold while held, so there’s no guessing on release.
  • Icons are produced at runtime, not bundled. deck icon emits a data:image/png;base64 URL that feeds straight into setImage. Web targets use the DuckDuckGo icon service (icons.duckduckgo.com/ip3/<host>.ico) — it returns a real 200 image/png with no redirect (Google’s needs a 301 follow), so a single stdlib urllib GET suffices. App targets render the macOS app icon via NSWorkspace.iconForFile_ into an explicit N×N NSBitmapImageRep — which captures asset-catalog icons that ship no .icns. Both are cached under ~/.cache/deck/icons/.
  • deck close mirrors open. App → quit the whole app (a quit Apple Event); Safari → close the matched tab via AppleScript; Chrome → close the matched tab on the same PID-addressed ScriptingBridge window object that find() resolved. Idempotent: closing what isn’t open is a no-op success.
  • Placement waits out slow launches. After create(), deck polls aerospace list-windows for the new window, then moves it to the target workspace. The poll returns the instant the window appears, so the ceiling is generous — 15 s for apps, 8 s for browsers. An earlier 2 s cap lost the race against Outlook’s cold start: the window surfaced after deck gave up and landed on the current workspace instead of its configured one. The durable fix is to also pin app targets with an on-window-detected rule (see aerospace-snippet.toml) so AeroSpace places them regardless of launch speed; deck’s move then just adds the “jump to it” focus.
Permissions Pressing a Chrome/Safari (or app-close) target from a button sends an Apple Event attributed to Stream Deck.app, which hosts the plugin — so it’s a one-time Automation grant per controlled app, not per target. Developer mode must be enabled (streamdeck dev) before the CLI can link/restart the plugin; without it the restart deep-link is silently rejected.
